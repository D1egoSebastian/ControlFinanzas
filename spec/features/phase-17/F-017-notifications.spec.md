## Goal

The app already knows everything that should interrupt the user: installments coming due, subscriptions
and fixed expenses about to be charged, budgets crossing 80% / 100%, and unacknowledged anomalies. Today
each fact sits on its own screen and the user only finds it by going there. Phase 17 adds a bell with an
unread badge to the shell. On app start it fills with the few notices that matter now. The user can
dismiss individual notices (permanently) and silence whole kinds. No new business algorithm is
introduced: every rule reuses an existing read path and threshold, and a persisted `Notification` table
is reconciled on each detection run, mirroring the Phase 14 `AnomalyAlert` pattern.

### Confirmed product decisions

All decisions below are binding (D1-D22 from the proposal, OD-1..OD-3 binding from the orchestrator) and
are not reopened here:

- **Persistence (D1/OD-1):** new `Notification` table, one row per instance, reconciled on each run —
  sealed class, private setters, `Create`, `MarkRead`/`Dismiss`, a unique idempotency index, an atomic
  `ApplyReconciliationAsync` with one `SaveChanges`, detach-not-clear on `DbUpdateException`.
- **Surface (D2/OD-2):** bell + badge + flyout in a new header row of `MainWindow.axaml`, owned by
  `ShellViewModel`. No new route. The list is a route-agnostic `NotificationListViewModel`.
- **Budget key (D3/OD-3):** `(Budget, BudgetId, Month, Tier ∈ {Near, Exceeded})` — dismissing Near never
  hides a later Exceeded.
- **Digest (D4):** in scope, delivered as the last slice, depends on the four other sources.
- **OS toasts (D5):** out of scope.
- **Trigger (D6):** app start plus manual refresh only, no timer. Settings via new `SettingKeys` through
  `ISettingsStore`; `AppSettings` is never touched.
- **Kinds (D7):** `DebtInstallmentDue`, `RecurringChargeDue` (`Subscription` and `FixedExpense` share one
  read path), `BudgetThreshold`, `Anomaly`, `Digest`.
- **Due-item horizon (D8):** 3-day forward window `[today, today + 3]` inclusive; debt installments also
  look back 7 days (`[today − 7, today + 3]`) while `Pending`, shown as overdue; recurring rules use the
  forward window only.
- **Budget scope (D9):** current month only, highest reached tier only; an Exceeded row removes an
  undismissed Near row for the same budget/month.
- **Anomaly source (D10):** unacknowledged `AnomalyAlert` rows keyed by `AnomalyAlert.Id`; dismissing the
  notification does not acknowledge the alert; acknowledging the alert removes its undismissed
  notification on the next run; detection never runs `DetectAnomaliesUseCase`.
- **Reconcile rules (D11):** qualifying source with no row → add; undismissed row whose source no longer
  qualifies → remove; dismissed row → never recreated or modified.
- **Read vs. dismissed (D12):** opening the flyout marks every listed row read; per-item dismiss hides the
  row and suppresses its key permanently.
- **Purge (D13):** rows whose reference date is more than 60 days before today are hard-deleted at the
  start of each run.
- **Flyout cap (D14):** at most 20 undismissed rows, unread first then by reference date ascending; badge
  shows the full unread count, rendered `9+` above 9.
- **Localization (D15):** `Notification` stores facts only; the UI item VM formats text at display time
  from resx (`es-DO`/`en`).
- **Toggle defaults (D16):** all four per-kind toggles default on; missing/invalid value means on.
- **Digest frequency (D17):** `Off`/`Daily`/`Weekly`, default Weekly.
- **Digest timing/content (D18):** generated by the first run on/after the period start when the stored
  cursor is behind; holds counts/totals only; missed periods are never backfilled; zero counts advance the
  cursor without creating a row; a new digest removes the older undismissed digest; the cursor is written
  only after a successful reconcile.
- **Manual refresh (D19):** a flyout-header button re-runs detection, guarded against concurrent runs;
  opening the flyout does not re-detect; saving Notificaciones settings also triggers one run.
- **Execution context (D20):** each run uses its own DI scope (fresh `AppDbContext`); reads are
  sequential; the run is fire-and-forget after the main window shows; every failure is logged and
  swallowed.
- **Click-through (D21):** none in v1.
- **Settings UI (D22):** a new "Notificaciones" section in `SettingsView` with 4 toggles and a frequency
  picker, saved per section.

## Requirements

### R-1 — Persisted, reconciled `Notification` table

The system MUST persist notifications in a `Notification` table reconciled on every detection run,
mirroring `AnomalyAlert`: a sealed entity with private setters, a `Create` factory, `MarkRead` and
`Dismiss` behaviors, a unique idempotency index on the source key, and an atomic
`ApplyReconciliationAsync` that performs exactly one `SaveChangesAsync` per run. On `DbUpdateException`
the repository MUST detach only its own newly-tracked entries and MUST NOT clear the shared
`AppDbContext`'s change tracker.

### R-2 — Five notification kinds

The system MUST support exactly five kinds: `DebtInstallmentDue`, `RecurringChargeDue` (covering both
`Subscription` and `FixedExpense` sources through one shared read path), `BudgetThreshold`, `Anomaly`, and
`Digest`.

### R-3 — Shell surface owned by `ShellViewModel`

The system MUST expose a bell icon, an unread-count badge, and a flyout list in a new header row of
`MainWindow.axaml`, owned by `ShellViewModel`. No new route MUST be introduced. The flyout's list content
MUST be backed by a route-agnostic `NotificationListViewModel` so it can be reused by a future
"see all" page.

### R-4 — Due-item horizon and overdue look-back

For `DebtInstallmentDue`, the system MUST notify installments whose due date falls in
`[today − 7, today + 3]` inclusive while the installment is still `Pending` (day 3 forward is included,
day 4 is not; the look-back covers up to 7 days overdue). An installment more than 7 days overdue MUST NOT
be notified. For `RecurringChargeDue`, the system MUST use the forward-only window `[today, today + 3]`
inclusive, with no overdue look-back.

### R-5 — Budget idempotency key and highest-tier-only

For `BudgetThreshold`, the idempotency key MUST be `(BudgetId, Month, Tier)` with
`Tier ∈ {Near, Exceeded}`, scoped to the current month only. Only the highest tier currently reached MUST
be represented by a live (undismissed) row. When a budget reaches `Exceeded`, any undismissed `Near` row
for that same budget and month MUST be removed by the reconcile step.

### R-6 — Anomaly source stays read-only over `AnomalyAlert`

For `Anomaly`, the system MUST read unacknowledged `AnomalyAlert` rows and key notifications by
`AnomalyAlert.Id`. Detection MUST NOT invoke `DetectAnomaliesUseCase`. Dismissing an `Anomaly` notification
MUST NOT acknowledge the underlying alert. When an alert is acknowledged elsewhere (the Dashboard), its
undismissed notification MUST be removed on the next detection run.

### R-7 — Reconcile rules: add, remove, never recreate dismissed

On each run, for every enabled kind: a qualifying source with no existing row MUST produce a new row; an
undismissed row whose source no longer qualifies (paid, deactivated, cursor advanced, below threshold,
acknowledged, or its kind toggled off) MUST be removed; a dismissed row MUST NEVER be recreated or
modified for as long as its idempotency key remains dismissed.

### R-8 — Read vs. dismissed semantics

Opening the flyout MUST mark every row currently listed as read, removing it from the unread badge count
without hiding it. Dismissing a row MUST be a distinct, per-item, permanent action that hides the row from
the flyout and permanently suppresses its idempotency key from ever being recreated.

### R-9 — 60-day purge

At the start of every detection run, the system MUST hard-delete any `Notification` row whose reference
date (due date, budget month start, or digest period start) is more than 60 days before `IClock.Today`.

### R-10 — Flyout cap and badge count

The flyout MUST display at most 20 undismissed rows, ordered unread-first then by reference date
ascending. The badge MUST show the full undismissed-and-unread count regardless of the flyout cap,
rendered as the literal string `9+` whenever that count exceeds 9.

### R-11 — Facts stored, text formatted at display time

`Notification` MUST store only facts (kind, sanitized subject label capped at 120 chars, reference date,
amount and currency, percent, tier, and digest counts) and MUST NOT store any user-facing literal text.
The UI item ViewModel MUST format the displayed text at render time from `Strings.resx` /
`Strings.es-DO.resx`.

### R-12 — Per-kind toggles via `SettingKeys`/`ISettingsStore`, default on

Each of the four detectable kinds (`DebtInstallmentDue`, `RecurringChargeDue`, `BudgetThreshold`,
`Anomaly`) MUST be gated by its own boolean setting (`notifications.debtDue.enabled`,
`notifications.recurringDue.enabled`, `notifications.budget.enabled`, `notifications.anomaly.enabled`)
read and written through new `SettingKeys` via `ISettingsStore`. `AppSettings` MUST NOT be modified or
extended for this feature. A missing or invalid stored value MUST be treated as on.

### R-13 — Digest frequency, generation, and no-backfill cursor

Digest frequency MUST be configurable as `Off`, `Daily`, or `Weekly` via
`notifications.digest.frequency`, defaulting to `Weekly`. A digest row MUST be generated only by the first
detection run on or after the current period start (calendar day for Daily, ISO week starting Monday for
Weekly) when the stored `notifications.digest.lastPeriodStart` cursor is behind the current period start.
The digest MUST hold only counts and a per-currency total of payments due in the period window, the count
of budgets at Near or Exceeded, and the count of unacknowledged anomalies for the current month. Missed
periods MUST NOT be backfilled retroactively. When every count is zero, no row MUST be created, but the
cursor MUST still advance. A newly generated digest MUST remove any older undismissed digest row. The
cursor MUST be persisted only after the reconcile for that run succeeds.

### R-14 — Manual refresh and settings-save trigger

The flyout header MUST expose a refresh action that re-runs detection, guarded so a second invocation
while one is already in flight is a no-op. Opening the flyout MUST NOT itself trigger detection. Saving
the Notificaciones settings section MUST trigger exactly one detection run.

### R-15 — Own DI scope, sequential reads, swallowed failures

Each detection run MUST execute inside its own dependency-injection scope with a freshly resolved
`AppDbContext`, MUST read each enabled source sequentially (not via `Task.WhenAll`), and MUST run
fire-and-forget after the main window is shown. Any exception raised during detection or reconciliation
MUST be caught, logged, and swallowed; it MUST NEVER propagate to crash or block application startup.

### R-16 — No click-through in v1

Clicking a notification row in the flyout MUST NOT navigate to any route or view in this phase.

### R-17 — Settings UI section

`SettingsView` MUST gain a "Notificaciones" section with the four per-kind toggles and the digest
frequency picker, saved using the existing per-section save pattern in `SettingsViewModel`.

### R-18 — Explicit scope exclusions

OS-native toasts, an "all notifications" route, click-through navigation, snooze, per-item horizons, and
any timer- or idle-based re-evaluation MUST NOT be implemented in this phase. No change MUST be made to
`AppSettings`, or to the `DebtPayment`, `RecurringRule`, `Budget`, or `AnomalyAlert` invariants, or to the
Phase 14 anomaly acknowledge semantics. No AI-generated notification text MUST be introduced.

## Scenarios

### S-1 — Roadmap completion criterion: relevant notices on app open

- GIVEN a debt installment due in 2 days, a subscription charging in 1 day, a budget at the Exceeded
  tier, and an unacknowledged anomaly, all for the current user data
- WHEN the app starts and detection runs
- THEN the bell badge shows the combined unread count and the flyout lists all four notices

### S-2 — Roadmap completion criterion: budget alerts fire at 80% and 100%

- GIVEN a budget whose spend crosses from below 80% to 85% of its limit in one run
- WHEN detection reconciles budgets
- THEN a `BudgetThreshold` notification with `Tier = Near` is created; WHEN a later run finds spend at
  105%, THEN a `BudgetThreshold` notification with `Tier = Exceeded` is created and the `Near` row is
  removed if still undismissed

### S-3 — Roadmap completion criterion: silencing a kind stops new notices

- GIVEN `notifications.budget.enabled = false` is saved in Settings
- WHEN a budget subsequently crosses into Exceeded and detection runs
- THEN no new `BudgetThreshold` notification is created

### S-4 — Idempotency across two runs

- GIVEN one qualifying debt installment due in 2 days and no change to its state between runs
- WHEN detection runs twice in sequence
- THEN exactly one `DebtInstallmentDue` row exists for that installment after both runs, with no duplicate
  and no update to its `CreatedAt`

### S-5 — Dismissed notification is never recreated

- GIVEN a `DebtInstallmentDue` notification that the user has dismissed, while the installment is still
  `Pending` and still inside the qualifying window
- WHEN detection runs again
- THEN no row for that installment's idempotency key is recreated

### S-6 — Near dismissed, then Exceeded crossing creates a new notification

- GIVEN a budget's `Near` notification was dismissed for the current month
- WHEN the same budget later crosses into `Exceeded` in that same month
- THEN a new `BudgetThreshold` notification with `Tier = Exceeded` is created, unaffected by the earlier
  dismissal of `Near`

### S-7 — Toggled-off kind removes existing undismissed rows and blocks new ones

- GIVEN two undismissed `RecurringChargeDue` notifications exist (one read, one unread)
- WHEN `notifications.recurringDue.enabled` is set to `false` and saved, triggering a run
- THEN both undismissed `RecurringChargeDue` rows are removed by the reconcile step and no new
  `RecurringChargeDue` row is created on this or later runs while the toggle stays off; re-enabling the
  toggle allows a future run to recreate rows for sources that still qualify and were not dismissed

### S-8 — Installment 8 days overdue is not notified

- GIVEN a debt installment still `Pending` with a due date 8 days in the past
- WHEN detection runs
- THEN no `DebtInstallmentDue` notification is created or kept for that installment, because it falls
  outside the 7-day overdue look-back

### S-9 — Digest created once per period, never backfilled

- GIVEN the digest frequency is `Weekly` and the stored cursor points to a period start 5 weeks in the past
  (the app was not opened for over a month)
- WHEN the app starts and detection runs
- THEN exactly one digest is created (or none, if all counts are zero) covering only the current ISO week,
  the cursor advances directly to the current period start, and no digest rows are created for the
  intervening missed weeks

### S-10 — Purge removes rows older than 60 days

- GIVEN an undismissed notification whose reference date is 61 days before today
- WHEN a detection run starts
- THEN that row is hard-deleted before reconciliation runs, and it does not count toward the badge or
  appear in the flyout

### S-11 — Badge shows 9+ above 9 unread

- GIVEN 12 undismissed, unread notifications exist across any kinds
- WHEN the shell renders the badge
- THEN the badge displays the literal text `9+`, and the flyout still lists at most 20 rows, unread-first

### S-12 — Detection failure never crashes startup

- GIVEN the reconcile save for one detection run throws (for example, a `DbUpdateException` from a
  concurrent write)
- WHEN that run fails
- THEN the exception is caught and logged, the main window finishes loading normally with whatever
  notifications already existed, and a subsequent manual refresh can still run and succeed

## Reconciliation with design (2026-09-26, orchestrator)

The design's 13-point Spec Reconciliation is accepted as binding, including its two
reviewer-flagged items (both confirmed correct on review):

- Fact refresh on undismissed rows (R-7): a Near budget notice showing 85% while the
  budget has since moved to 95% would be a live-data bug, not a feature — refreshing
  facts on undismissed rows without touching `Id`/`CreatedAt`/`ReadAt` avoids stale
  numbers while never re-badging an already-read row.
- The digest ignores per-kind toggles and dismissals: it has its own on/off switch,
  and double-suppression logic (toggle AND dismissal AND digest-off all interacting)
  would be a correctness risk for no real benefit.

Also accepted: single `DedupKey` string instead of a composite unique index (SQLite
NULL-distinctness); anomaly source excludes alerts older than 60 days so purge can
never resurrect one; a deactivated recurring rule (`EndDate < NextGenerationDate`) is
excluded from detection; an indeterminate (missing-FX-rate) budget keeps its existing
notice rather than being removed; purge computed and applied within the same single
`SaveChangesAsync`; digest window/cursor details (`[today, today+6]` weekly, `today`
daily, `yyyy-MM-dd` cursor); manual refresh is a no-op while a run is in flight,
startup/settings-save are queued and run once after; opening the flyout marks only
the ≤20 listed rows (badge may stay non-zero with >20 unread); `NavigationServiceTests`
needs no change but both `SettingsViewModel` fixtures do; the flyout is a
`ToggleButton` + `Popup` with two-way `IsOpen`, not `Button.Flyout`; "overdue" is
derived at display time, never stored; no `Subscription`/`FixedExpense` subtype
distinction is persisted.

## Out of Scope

OS-native toasts, an "all notifications" route, click-through navigation, snooze, per-item horizons, and
timer- or idle-based re-evaluation. Any change to `AppSettings`, or to the `DebtPayment`, `RecurringRule`,
`Budget`, or `AnomalyAlert` invariants, or to the Phase 14 anomaly acknowledge semantics. AI-generated
notification text.

## Acceptance Criteria

- [ ] **(roadmap)** When the app opens, the bell shows the relevant notices for today (due items within 3
  days, overdue installments, the current budget tier, unacknowledged anomalies, and the digest when due).
- [ ] **(roadmap)** Budget notices fire when spending crosses 80% and 100%, and a dismissed Near never
  hides a later Exceeded.
- [ ] **(roadmap)** The user can silence each notice kind and the digest; a silenced kind produces no new
  rows and its existing undismissed rows are removed.
- [ ] Rerunning detection is idempotent (S-4), and a dismissed notice never reappears (S-5).
- [ ] Horizon edges are correct: day 3 forward is included, day 4 is not; installments beyond 7 days
  overdue are not notified (S-8).
- [ ] The digest is created at most once per period with no backfill after a long absence (S-9), and the
  60-day purge and reconcile-conflict handling leave the shared `AppDbContext` usable (S-10, S-12).
- [ ] The badge renders `9+` above 9 unread and the flyout caps at 20 rows, unread-first (S-11).
- [ ] Build is clean, the full suite is green, `dotnet format style --verify-no-changes` exits 0,
  NetArchTest R-1..R-5 is green, and `ModelSnapshotConsistencyTests` is green.
